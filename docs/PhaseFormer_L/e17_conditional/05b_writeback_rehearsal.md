> 工具：`scripts/phaseformer_L/rehearse_e17_writeback.py`｜真实产物：`research_runs/phaseformer_L_e17_conditional_v1/projectors/projector_audit.json`（33572 B）｜预演输出：`/tmp/rehearse_e17/`
> 状态：**通过**（服务器执行，退出码 0）｜本预演**不训练任何模型**，只验证回填工具的 join 与断言

## 1. 为什么要在正式回填之前做这件事

`e17_writeback.py` 的 §4.5 表来自**两个输入的 join**：

* 结果 CSV —— `horizon` 从 CSV 读出时是**字符串**，第 77 行 `int(row["horizon"])` 转成整数；
* 投影器审计 JSON —— `horizon` 是 JSON 数字，第 115 行 `int(entry["horizon"])`。

两边都转 int 所以键能对上，但这是**类型边界上的隐式约定**。一旦不一致，
`cosines.get((dataset, horizon))` 会对**每一个** setting 返回 `None`，而回填工具的处理是
把该列写成 `None`/`—`——**不会抛异常**。

后果很具体：§4.5 中"两个冻结方向在 6/7 个 setting 上近乎冗余、只有 Electricity-336
（│cos│=0.0066）真正能区分两臂"这一**论断的全部证据**会变成一列空值，
而流水线仍然报成功。这正是"静默丢失证据"那一类缺陷，因此必须在跑之前验。

同时，投影器审计是**已冻结的真实产物**（`Q1*/Q1COND/Q1INDREVIN` 基向量与其审计），
所以本次预演**用真实文件、不造假**：只合成结果行，且合成用的列名取自
`e17_conditional.RESULTS_FIELDS`（生产者自身声明），因此不可能与生产者漂移。

## 3. 需要如实记下的一点：**第一次运行是我自己的断言写错了**

第一次运行报 **7/7 MISMATCH**，看起来像回填工具有严重缺陷。逐格核对后发现
**数值本身完全相等**（如 `got=0.999619`、`audit=0.999619`），失配来自我的断言：

* 回填工具**按设计**把余弦四舍五入到 6 位小数（`round(cosine, 6)`）；
* 我的断言却用 `abs(got - want) < 1e-9` 去比**未舍入**的审计全精度值，
  于是把**正确的**回填判成了错误。

修法是把断言改为与**舍入后的**审计值比较（`abs(got - round(float(want), 6)) < 1e-12`），
并在脚本注释里写明这次教训。

这件事本身值得记录：**验收脚本的断言错了，会制造出与真实缺陷外观相同的告警**。
若当时不做逐格数值核对而直接相信"7/7 MISMATCH"，就会去"修"一个并没有坏的工件；
反过来，若因为"工具已经跑通"而放宽成永远通过，就失去了检测力。
两者都指向同一条纪律：**验收断言必须先对着已知正确的输入校准一次**（本会话对
`check_column_contracts.py` 用的是同一套做法——双向突变正对照）。

## 4. 边界（本预演**没有**证明什么）

* 结果行的**数值**是合成的，因此它不验证 §4.5 表的四臂数字本身是否正确——
  那要等 24 个 run（阶段 4）跑完后由阶段 5 审校按冻结阈值判定；
* 它不验证 `h1_cond_gt_indep_seed_majority` 的语义（合成里只是占位），
  H1 的三档结论仍是 `04_run.md` 的职责；
* 它只覆盖 `(dataset, horizon)` 这一个 join 键。若后续 §4.5 表再引入别的 join，
  需另做一次同样的"真实文件 + 精确 schema 合成"预演。
